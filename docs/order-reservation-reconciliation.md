# V4 下单预留对账尝试

此方案是用于验证的草稿，不代表 Redis、MySQL 和 Kafka 之间具备强一致性或生产级故障恢复。

## 处理流程

- V4 先生成订单号；Redis Lua 同时占座、写入座位归属、预留记录和检查时间。
- 订单消息发送至独立的 `create_order_reservation` 主题，避免旧消费者绕过预留状态检查。
- 记录状态为 `PENDING` 时，消费者和超时补偿通过 Redis Lua 竞争状态：消费者先领取则进入 `PROCESSING`；超时任务先关闭则释放属于该订单的座位并进入 `CANCELLED`。迟到消息不能创建已关闭的订单。
- `PROCESSING` 不会被超时任务释放。消费出错或中断后，后台使用同一个订单号重发；订单服务基于订单号和数据库唯一约束处理重复创建，并在安排未支付订单取消后标记 `COMPLETED`。
- 确认调用 Kafka `send()` 前预检查失败时，可以直接关闭仍处于 `PENDING` 的预留；无法确认发送结果时保留预留等待对账。

默认预留 30 秒，后台每 5 秒检查一次；可通过 `damai.order.reservation-timeout-millis`、`damai.order.recovery-interval-millis` 调整。`PROCESSING` 默认每 10 秒尝试一次重发。这些值不代表整个 HTTP 接口的响应上限。

## 本地验证

- Java：`mvn -pl 'damai-server/damai-program-service,damai-server/damai-order-service' -am test`
- Redis Lua：`python3 tests/test_issue10_release.py`（需要本机 `redis-server`，测试自动启动独立实例）。
- 在独立 MySQL、Redis、Kafka 和 Nacos 环境中，已验证：
  1. 将回调等待设为 0，停掉订单消费者后下单：接口返回结果待确认；预留到期后恢复座位；重启消费者后迟到消息被跳过且订单表无该订单。
  2. 模拟消费者已领取后中断：到期后座位仍被占用；后台重投，消费者恢复后只创建一笔订单。
  3. 程序服务在预留待处理时重启：恢复后能继续发现过期记录并释放座位。

## 未解决问题

- 预留记录和检查队列都在 Redis；Redis 丢数据、主从切换丢写或持久化配置不当时，不能保证恢复。`CANCELLED` / `COMPLETED` 记录暂不清理，避免迟到消息绕过状态检查，但会持续消耗内存，需要设计安全保留期和归档。
- 消费已进入 `PROCESSING` 而数据库持续不可用时，系统会保留座位并重试，不会自动确认失败。缺少重试上限、告警、人工处理和可视化对账后台。
- 状态记录反映当前流程进度，并没有独立核对所有 MySQL 和 Redis 座位、库存数据；也没有面向前端的状态查询接口或稳定请求幂等键；用户收到结果待确认后不能通过本方案自动查询，也不能保证重复提交复用同一订单。
- MySQL 事务与 Redis 库存、限购计数及延迟队列并非同一事务，极端故障仍可能造成不一致；需额外对账、持久化发送记录与故障测试。订单表必须具有订单号唯一约束。
- 本方案沿用项目已有 Redis 脚本的动态键访问方式，未经 Redis Cluster 验证。隔离实验直接访问业务服务，未覆盖网关、浏览器与多实例滚动升级。
